# SJN MedNest Management Panel — Step 2: Isolated Staff Auth and Chief Email Privacy

**Date:** 2026-11-07 (Asia/Karachi)  
**Branch:** `sjn-phase1a-foundation`  
**Status:** Architecture recommendation documented following owner's request to finalize Step 2. **No new Supabase project, new staff user, email sender, live auth cutover, student schema edit or production deployment has been authorized/executed by this document.** Actual provisioning depends on owner-supplied Supabase organization ID, quoted project cost and explicit cost acknowledgement; owner must approve the specific execution boundary before infrastructure work.   
**Priority:** Preserve existing Student LMS, signed-in Chief Administrator experience, immutable exams/history, and no measurable student latency regression.

## A. Current read-only evidence (7 Nov 2026)

- GitHub management frontend `apps/management/auth-client.js`: `me` returns the signed-in user's own verified email; My Profile displays only that user's email. The Chief Administrator identity card on Team & Permissions is populated from the **Chief-only** `team.list` action.
- `database/management/mednest-edge-function/index.ts`: `team.list` rejects ordinary members. The management member, audit, invitation and step-up tables have RLS enabled and **no direct `authenticated` SELECT privileges**.
- **Privacy gap to close before any invitations:** `audit.list` permits a member with `audit.view` and returns raw event `details` and actor/target IDs, without response-field sanitization. Current observed audit detail *keys* were `method`, `staff_mfa_required`, `display_name`, and `organizational_title`; this does not establish a permanent guarantee that future events could not include email/PII. Do not claim that the entire API is already privacy-hardened.
- Staging read-only verification: **one Chief Administrator, zero invitations**, and automatic `on_auth_user_created` trigger persists. The trigger creates a student profile for new accounts in the existing staging Auth realm.
- Existing management `members`, `audit`, `invitations`, and `stepup` tables have foreign keys referencing the current project `auth.users`. **Do not swap frontend Supabase project URL without migrating identity-dependent tables/functions.**
- Supabase organization is currently **Free**; connected inventory showed one active student staging project and one inactive older project. The inactive project must not be repurposed, restored or deleted by assumption. Supabase docs currently provide two free active projects across an eligible account's organizations, paused projects not counting. Quoted cost/entitlement must still be independently checked through the connected cost flow with the **organization ID provided by the owner**. No cost check or new resource creation performed.

## B. Non-negotiable Chief Administrator privacy

- Ordinary Management Team Members must not see the Chief Administrator's login email in profiles, Team pages, member lists, management dashboards, activity events, permissions, exports, notification previews or ordinary API responses. Avoid hard-coding any private email in HTML, JS, logs, build output or source documentation.
- A member sees **their own** verified email in My Profile. Chief Administrator may see members' login emails for invitations and staff account governance. Mere `audit.view` or title is not an entitlement to account identifiers.
- Show Chief Administrator **display name (or formal role)**, optionally organizational title, and role only to team members. Never use user-supplied display names, titles or user metadata to assign roles.
- **Before staff onboarding:** change `audit.list` to return a stable role-specific allowlist of safe fields and redact emails/other identity metadata server-side, not just hide UI text. Prefer separate confidential security-audit access for Chief-only and sanitized operational-event views for explicitly permitted members. Review all future staff API outputs and error messages for PII. Regression tests: ordinary staff `me`, `team.list` (403), `audit.list` with and without permission, browser/serialized API responses, suspended/expired sessions, cross-user actions and source scans.
- Provider account administrators and authorized infrastructure operators may retain back-office access under provider roles; the requirement concerns **ordinary Academy Management Team Members**. Do not promise an absolute email invisibility guarantee from the underlying account provider or email itself.

## C. Recommended permanent architecture

1. **Isolate identities** using a newly created Supabase project dedicated to management staff only (`SJN MedNest Management Auth`, subject to owner's naming/cost approval). It has independent Auth, staff profile/membership records, sensitive-operation step-up, invitations, audit data and management Edge Function. **No trigger that creates `public.profiles` student rows** and no link to existing student sign-up flows.
2. **Isolate frontend sessions**: `apps/management/` authenticates only to management Supabase Auth, with a separate storage key and verified management issuer. Email/password daily Sign In remains; no QR/TOTP. Verify server-side issuer, audience, signature, expiration, Auth `getUser`, `session_id`, verified email, active Chief/member role, and per-action authorization. A login email or browser permission toggle alone never grants staff rights.
3. **Move and adapt management schema**: provision versioned, RLS-protected staff-only tables/functions in the new project. Update Auth foreign keys, session binding, step-up RPCs, invitation acceptance and audit atomicity to reference **new management `auth.users` only**. Do not copy student Auth users, student records, passwords, student tokens, or existing Auth UUID assumptions.
4. **Bridge later student operations server-to-server only**: when authoring, courses and access features are separately approved, a restricted management backend validates fresh staff access and maps each permitted operation to a narrow, transactional, audited student-staging RPC. Secrets remain server-side. Management JWTs are **not** assumed valid in the student project; do not enable broad cross-project client access or frontend direct student service-role keys. Restrict CORS/origins, enforce idempotency/rate limits and safe source-preserving revisions.
5. **Chief Administrator cutover**: explicitly approve and verify the sole new Chief management Auth identity with an email proof and account UUID, protected bootstrap transaction, unique-Chief constraint and audit; retain an emergency rollback/access plan. An old staging Auth UUID is **not** a valid substitute for new-project identity. Maintain the pre-cutover login until new password Sign In, profile, email-stepup and single-Chief authorization pass authenticated owner QA. Do not delete the original student project's Auth identity or change its creation trigger.
6. **Invitations**: Chief-only, individually granted capabilities, verified academy sender domain (Resend or explicitly approved provider), unique 72-hour single-use invitation, exact email matching, independent staff credential setup and revocation/suspension. Until provider, deliverability, sender domain, and end-to-end tests succeed, **keep `STAFF_IDENTITY_ISOLATED=false` and invitation controls disabled on the current service**. Do not enable invitations in the shared student Auth project.
7. **Sensitive staff-security approval**: retain eight-digit emailed security code with ten-minute validity and rate limits; once verified, only sensitive staff-access modifications are authorized for **30 minutes in that exact staff session**, with server and DB checks. Ordinary profile name/title, basic work and daily Sign In need no extra email step-up.
8. **Release and performance gates**: test negative authorization (student JWT against staff API, staff JWT against student API, revoked/suspended staff, forged issuer/audience, new unauthenticated identity), profile email privacy, audit redaction, invitation expiration/reuse/revocation, transactional audit, desktop/mobile, current exam baseline p50/p95 with representative concurrent admin work, and rollback. No student schema/auth trigger change, no student exam/result/history code change, no production `main` merge without separate explicit owner authorization.

## D. Practical implementation order and owner dependency

- **Current permitted planning result:** document this architecture and privacy gap; do not claim a deployed isolated staff identity provider.
- **Pre-provision:** owner supplies exact Supabase **organization ID** from their organization settings; connected tool returns a project-cost quote, which must be shown and acknowledged before creation. Do not quietly repurpose the inactive older project.
- **After cost and infrastructure approval:** create dedicated management Supabase project; apply staff-only migration and Edge Functions; implement Chief protected bootstrap and switch management preview only to new staff Auth with a reviewed staged cutover.
- **Before any ordinary staff invitation:** harden all audit/profile/directory response privacy, verify personal Chief email cannot reach member-visible payloads, configure academy sender, test a limited permitted invite end-to-end, then enable invitations narrowly.
- **After staff foundation signoff:** separately scope Question Content Studio, robust 500–3,000+ MCQ imports, student entitlements, reporting, academic review and subsequent operations.
